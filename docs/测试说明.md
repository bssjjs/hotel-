# 测试说明

本文说明 hotel-insight 的测试体系：**测什么、怎么跑、契约与单元各自锁定什么承诺、改代码时要注意什么**。

- 工程规范见《AGENTS.md》；测试的存在依据是"流水线可验证"这条交付要求（第 0 节）。
- 测试覆盖数据链路（config / db / dwd / quality / checks / pipeline）与五个分析模块
  （origin / timing / room / cancel / rate），不覆盖 viz。

## 1 一句话概览

- **两类测试**：`test/contract/` 锁定"模块对下游的承诺"，`test/unit/` 锁定"单个函数的行为"。
- **规模**：96 个测试 —— 单元 74、契约 22（其中 4 个是真实库对账，默认跳过）。
- **零外部依赖**：全部用内存/临时 SQLite + 合成数据，不读 `data/`，任何人 clone 下来就能跑。
- **一行命令**：`python -m pytest`，不需要 editable 安装、不需要设 `PYTHONPATH`。

## 2 怎么跑

在项目根目录：

```bash
python -m pytest                          # 全部测试（92 个，约 6 秒；4 个 smoke 默认跳过）
python -m pytest --run-smoke              # 加跑真实库对账（需要 data/hotel.db）
python -m pytest test/contract            # 只跑契约测试
python -m pytest test/unit/test_dwd.py -v # 只跑一个文件
```

- 导入路径由 `pyproject.toml` 的 `[tool.pytest.ini_options] pythonpath = ["src"]` 解决，
  测试代码里没有 `sys.path` hack。
- `--run-smoke` 才执行 `test_real_db_smoke.py`；默认跳过，CI 与没有 `data/` 的机器不受影响。
- 测试**不写** `data/hotel.db`：所有写入都在临时库上。

```

│   ├── test_pipeline_contract.py     # run_day 端到端：六步、四表、幂等（5）
│   ├── test_quality_contract.py      # dq_check_result 表结构（3）
```

## 4 契约测试：锁定了哪些承诺

**契约 = 一个模块对下游的承诺。** 下游按承诺写代码；改实现可以，改承诺就是破坏契约。
契约测试从"下游消费者"的视角断言这些承诺，比单元测试更容易抓住"重构时悄悄变了行为"。

| 契约方 | 承诺 | 测试文件 | 失败意味着 |
| --- | --- | --- | --- |
| `bookings` 结构 | 37 列、顺序固定 | `test_schema_contract.py` | 流水线 `SELECT *` 会读错列 |
| `dwd.clean_bookings` → 下游 | 输出列序 == `DWD_COLS`；`booking_id` 唯一；`month` == `arrival_date[:7]`；剔除记录键 == {步骤, 剔除行数, 剩余行数} 且行数自洽 | `test_dwd_contract.py` | 分区写错表、报表对不上 |
| `db` 写入 → 读回方 | 同月重跑不翻倍；换月互不影响；replace 全量替换、append 只增 | `test_db_contract.py` | 重跑一次行数就翻倍 |
| `pipeline.run_day` | 六步顺序固定：`extract_bookings → clean_bookings → write_dwd → write_clean_steps → audit → save_audit`；产出四张表；同日重跑幂等；返回值 == `etl_log` | `test_pipeline_contract.py` | 平台方改了结构或漏写表，下游全断 |
| `quality.dq_record` ↔ 表 | `dq_check_result` 列序 == `quality.COLUMNS`；同 `check_id` 覆盖、不同共存；表不存在时自动建 | `test_quality_contract.py` | 报告读错列、旧结论叠加 |
| 真实库（本地对账） | 结构、119,390 行、四个缺失字段、重复 31,994 行、清洗后 85,585 行 | `test_real_db_smoke.py` | 数据库换了一批数据，报告要重出 |

### 4.1 步骤顺序为什么是契约

`run_day` 的六步顺序写进 `etl_log`。有人要"优化"顺序时，先改
`test/contract/test_pipeline_contract.py` 的 `EXPECTED_STEPS` 与
`test/contract/schema.py` 的同名常量，再改代码——否则测试先红。

### 4.2 契约常量的来源与更新

`schema.py` 的结构抄自真实库的 `PRAGMA table_info`（**只抄结构、不抄数据行**，符合 AGENTS.md 15.3）。
平台方改了 ODS 结构时：先跑 `python -m pytest --run-smoke` 看对账报错，确认改动后同步 `schema.py`。

## 5 单元测试：锁定了哪些行为

| 模块 | 锁定的行为 |
| --- | --- |
| `config` | 标记文件命中根；缺标记抛 `FileNotFoundError`；32 个业务字段；`DWD_COLS` 列序；阈值可从 settings 读到 |
| `dwd` | 中文月份 → 1–12；已存在的派生列不重算；四步剔除数 **1/1/1/2** 与顺序；去重保留最小 `booking_id`；`adr` 边界（>0 且 ≤1000）；不改入参 |
| `quality` | 空白字符串算缺失；0 行缺失率为 0；重复列名按位置统计；list 不可哈希按字符串去重；`fmt_pct` 五个取位档；非法状态抛 `ValueError`；同编号覆盖 |
| `db` | `table_exists`；replace 不叠加、append 翻倍；同分区幂等；换月互不影响 |
| `checks` | 16 项齐全且编号 `DQ-01`–`DQ-16`；`company_id` 全空 → DQ-02 不通过；`adr=0` → DQ-10 不通过；**DQ-06 的阈值来自 settings**（调到 5% 就从警告变不通过）；状态日期早于到达日 → DQ-09 报违规 |
| `rate` | Wilson 区间落在 [0,1] 且小样本更宽；`rate_table` 列序 == `RATE_COLS`；Kitagawa 三块之和 == 总变化（恒等式）；**分组键含 NaN 时收成"（缺失）"组**，否则三块拼不回总数 |
| `origin` | 前 N 之外合并成"其他"且永远垫底；占比分母是全量而非前 N；HHI 在单一客源时为 1 |
| `timing` | 季节指数只用完整年（不完整 `raise`）；周内固定七行；`comparable_slice` 只留指定年份与月份；分档保留 `settings` 里的顺序 |
| `room` | 换房率只在未取消单上算；房型 <`min_group_n` 不上表；换房矩阵行内归一 |
| `cancel` | 12 个因素齐全且性质在四类之内；超额取消单用 `max(0,·)` 不互相抵消；时机分档覆盖 100%；情景随假设线性增长 |

新增分析模块的测试都在 `test/unit/`：这些函数是纯计算（AGENTS.md 4.1），几个合成行就能测，
不需要造数据库——这也是把它们与 `dwd` 分开写的好处。

## 6 测试数据设计

### 6.1 合成 bookings（`sample_data.py`）

25 行，构造得让每一步剔除数都算得清：

| 内容 | 行数 |
| --- | ---: |
| 干净记录（一月/二月各 10 条，覆盖两个分区） | 20 |
| 无人入住（成人+儿童+婴儿 = 0） | 1 |
| 零晚数 | 1 |
| 房价 0 值 | 1 |
| 与第 1 条完全重复 | 2 |

25 → ①−1 → 24 → ②−1 → 23 → ③−1 → 22 → ④−2 → **20**。

刻意保留的细节：`is_canceled` 用 `int`（不是 bool，否则契约的 dtype 断言会失败）、
`agent_id` 是 `240.0`（触发 DQ-04）、`arrival_month` 是"一月"（触发 DQ-05 的中文月份分支）、
`company_id` 全空（触发 DQ-02）。

### 6.2 合成分析面板（`make_panel`）

1,728 行，2 年 × 12 月 × 2 酒店 × 3 国 × 3 渠道 × 3 房型，再把葡萄牙复制一份
（本项目第一大客源，样本量必须是别国的两倍，"取前 N 名"才稳定）。

刻意保留的细节：

- **不掺脏数据**：分析模块要测的是"结构对不对"，不是"脏数据怎么洗"，洗数据的事归 `dwd`。
- **各取值样本量不同**：全相等时"排序取前 N"的结果会随实现变化，测试就没法写死顺序。
  第一版 `test_origin` 就是因为英国与德国行数相同而排序不稳，改成只锁"葡萄牙第一 + 其他垫底"。
- **取消规则是确定性的**，不用随机数：OTA 且 7 月及以后取消、葡萄牙且提前期 > 90 天取消，
  于是"取消率是多少"可以从规则直接推出来，断言不依赖随机种子。

### 6.3 为什么不用真实库

1. `data/` 不进 Git（AGENTS.md 1.1），测试读它就不能在别人机器上跑；
2. 测试要可重复——真实库会被流水线不断写入新表；
3. 真实库的数字属于"交付内容"，变了应该重新出报告，而不是改测试。

真实库的"对账"需求由 4 个 smoke 测试单独满足。

## 7 编写中固化的事实

1. **pandas 3 的 dtype 行为**：`to_sql` 写入的列读回来可能是 `Int64`；字符串列推断为 `StringDtype`
   （断言用 `is_string_dtype`，不要写 `== object`）。
2. **SQLite 存 NULL 读回是 NaN**：`etl_log` 里"输入行数"为 None 的行（例如读库那一步），
   读回后是 NaN，断言要用 `pd.isna`。
3. **`is_canceled` 不能是 bool**：真实库是 INTEGER，合成数据必须用 `int(...)`，
   否则 `is_integer_dtype` 失败——这个问题在写测试时实际踩过一次。
4. **`write_partition` 的幂等不是原子的**（先删后写），与上游项目同源，`db.py` 的 docstring 已注明。
5. **布尔 Series 不要拿去 `reindex` 做小样本过滤**：`tab.loc[counts >= min_n]` 会触发
   "boolean Series 与索引不对齐"的警告，改为 `tab.loc[counts[counts >= min_n].index]`。
6. **分解的分组键必须先处理缺失**：客源国缺 0.51%，NaN 自成一格却不进 `groupby`，
   三块就拼不回总变化。`rate._key` 把 NaN 收成"（缺失）"组——这个函数是被恒等式断言逼出来的。

## 8 不在测试范围（有意为之）

| 不测的东西 | 原因 |
| --- | --- |
| `viz`（theme / styles） | 渲染断言脆弱，且与数据链路无关；图表质量靠 `docs/图表规范.md` 的审图清单 |
| 性能基准 | 依赖机器，易碎；全量 85,585 行的清洗 + 稽核实测约 4 秒，记在 `etl_log` 里 |
| 真实数据行内容 | 只用聚合与结构断言（AGENTS.md 15.3） |

## 9 维护约定

1. **改产品代码行为前**：先跑测试。契约测试失败先判断"是改坏了"还是"承诺有意变化"；
   后者要同步改契约测试与本文档，并在提交说明里写清契约变化。
2. **平台方改了表结构**：`--run-smoke` 对账 → 更新 `schema.py` → 检查 `SELECT *`。
3. **新增模块**：单函数行为进 `test/unit/`，跨模块承诺进 `test/contract/`；
   共享 fixture 放对应目录的 `conftest.py`，不建 `utils.py`（AGENTS.md 6.2）。
4. **提交格式**：测试改动按 AGENTS.md 14.2 用 `test: 一句话说明`。
